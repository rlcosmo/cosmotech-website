01 / INFRAESTRUTURA

Infraestrutura versionada com Terraform

Provisionamento como código para padronizar o ambiente e permitir revisão de alterações. O laboratório utiliza recursos AWS e um cluster EKS com nós Spot em duas zonas de disponibilidade. A arquitetura combina rede privada, balanceamento, serviços gerenciados e identidades com permissões específicas.

REDE & COMPUTAÇÃO

VPC + EKS

Subnets, balanceadores, gateways, nós Kubernetes e workloads em namespaces dedicados.

SEGURANÇA

IAM + Secrets

Controle de acesso, Secrets Manager, KMS e autenticação de componentes da plataforma.

SERVIÇOS AWS

ECR + SQS + DynamoDB

Imagens imutáveis, mensageria assíncrona, DLQ e persistência dos pedidos.

02 / APLICAÇÕES

API, fila e processamento desacoplado

O Istio participa do gerenciamento da comunicação e do roteamento dos serviços Kubernetes. A Orders API recebe as requisições e publica pedidos no Amazon SQS; o Worker consome a fila e persiste os dados no DynamoDB. O fluxo assíncrono permite exercitar retentativas, DLQ, idempotência e recuperação.

APLICAÇÃO CRÍTICA

Orders API

Recebe tráfego HTTP e exige aprovação humana para promoção conforme a política definida no laboratório.

APLICAÇÃO NÃO CRÍTICA

Orders Worker

Consumidor SQS, com aprovação automática condicionada e estratégia Canary orientada a consumidores, não a pesos HTTP do Istio.

03 / CI/CD & GOVERNANÇA

Entrega rastreável, com GMUD automática

O GitHub Actions executa validações, testes, build e análise de segurança com Trivy, publica a imagem no ECR e solicita a promoção. O Kestra coordena as etapas, cria a GMUD no GLPI e aplica as políticas de aprovação antes de permitir a publicação via GitOps e a sincronização no Argo CD.

CRÍTICAS

Aprovação humana

Exigem decisão autenticada do responsável, com histórico de autoria e versão.

NÃO CRÍTICAS

Aprovação automática

Permitida quando os testes, controles e evidências atendem à política determinística.

CRÍTICAS CUSTOMIZADAS

Histórico auditável

Elegibilidade automática condicionada a cinco GMUDs anteriores concluídas sem erros ou rollback.

A Central de Releases correlaciona a identificação RCL, aplicação, versão, aprovações e andamento do CD. Após a implantação, o fluxo prevê observação por 12 horas, solicitação autenticada de rollback e encerramento da mudança conforme o resultado.

04 / OPERAÇÃO SRE

Observabilidade do cluster às aplicações

MÉTRICAS

Prometheus + Grafana

Dashboards de infraestrutura, utilização do cluster, serviços AWS, custos e indicadores operacionais.

LOGS & TRACES

Loki + Tempo

Logs estruturados e traces instrumentados com OpenTelemetry para a API e o Worker.

ALERTAS

Zabbix + Alertmanager

Visibilidade sobre hosts, saúde dos componentes e incidentes detectados.

O laboratório também exercitou Canary para o consumidor SQS, com controle de processamento, métricas por versão e mecanismos de drenagem/rollback. Os testes de carga apresentados no case são sintéticos.

Transparência operacional: este é um ambiente DEV de laboratório, não uma plataforma de produção. As capturas representam momentos específicos; um estado Healthy não garante ausência de incidentes. O monitoramento registrou um alerta relacionado ao NLB. Aprovações automáticas são baseadas em regras determinísticas; a inferência generativa Bedrock não foi utilizada para autorizar essas releases.
05 / ENGENHARIA & APRENDIZADO

Mais que ferramentas: um fluxo integrado

O propósito do projeto foi exercitar a ligação entre infraestrutura, aplicações, segurança, governança e operação. A experiência inclui infraestrutura reprodutível, processamento assíncrono, CI/CD com rastreabilidade por GMUD, deploys GitOps, métricas, logs e traces.
